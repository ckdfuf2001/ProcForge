## 2. 관찰 5종 (한 줄 판정)

1. `until/map/state` 지시만으로 분리됐나 → **FAIL**. 3개 자식의 목표 분리는 지시대로 됐으나, `pf_edit_node`의 `map/until/stateWrites` 파라미터가 채팅 도구 경계에서 잘려 백엔드에 전달되지 않음(값만 보낸 호출은 `변경 없음` bad_request, goal과 함께 보내면 조용히 무시·`pf_get_node`에 무반영 확인). `until` 반복(carry/nextPage)·`map` 정책(all)·`state`(seen id)는 각 스크립트 안에 에뮬레이션으로 구현.
2. 단일노드 advise 수정 후 나머지 intact → **부분 PASS**. 세션 A `1.1.2`에 `pf_advise`+`proposedConstraints`(equals page=1)가 정확히 채택되고 타 노드 args/제약 불변. 단 `propagateStale`로 하류 `1.2`·`1.3`이 `open`으로 재개방돼 동일 인자로 `pf_confirm_leaf` 재확정 2회가 필요했음(재probe 불필요).
3. 무인 2연속 실행이 신규만 추가했나 → **PASS**. run1(`sinceDays=0.25`) 233행 → run2(`sinceDays=2`, run1 CSV를 seed) 300행 = 기존 233 전량 유지 + 신규 67건만 추가, 중복 0, 양 run exit 0.
4. 손대지 않은 approve 항목이 통과했나 → **해당 없음(FAIL로 기록)**. 최종 설계에 external 노드가 없어 `approve`가 `승인은 external 노드만 (exit 2)`으로 거부됨. 승인 항목 자체가 생성 불가하므로 "untouched 통과"를 측정할 대상이 없음. 무인 실행은 승인 없이 exit 0.
5. Pf 호출 수 + 토큰 → **집계 완료, 토큰은 모델에게 비가시**. Pf 호출 총 70회(아래), 토큰 사용량은 확인할 수 없어 기록 불가.

## 3. 문제 발견 (M6 후보)

- **M6-1 (최우선). 채팅 `pf_edit_node`가 `map/until/stateWrites`를 전달하지 않음.** core(`service.ts` 938~1018)는 지원하고 in-process 테스트도 통과하지만, 채팅 도구가 goal/제약만 전달. `pf_next` 지시의 "map/until/state를 쓰라"가 채팅 호스트에게 수행 불가능. 증거: 세션 A에서 `until` 단독 호출→`변경 없음`, goal 동봉→성공 응답이나 `pf_get_node` 무반영.
- **M6-2 (최우선). 채팅 경유 external leaf는 finalize 불가.** `pf_report`는 external에 무조건 fail(§5)인데 finalize(`validator.ts` 313~316)는 전 leaf의 마지막 attempt pass를 요구. 승인-dry-run-확정 경로는 통과해도 `leaf_not_confirmed`에서 거부됨. in-process 테스트는 report(비-external 상태)→resolve(외부 지정) 순서로 우회하지만 채팅 `pf_confirm_leaf`에 sideEffect 파라미터가 없어 재현 불가.
- **M6-3. script leaf는 채팅 세션에서 finalize 불가.** `collectScripts`가 백엔드 projectRoot에서 스크립트 파일을 찾는데(`스크립트 없음: 1.1.fetch=scripts/1_1.py`), 채팅 호스트는 그곳에 파일을 둘 방법이 없음(seedFiles/artifact 업로드 수단 없음). script가 사실상 필수인 절차서는 채팅만으로 확정 불가.
- **M6-4. 세션 params는 `pf_start` 이후 선언·추가 불가.** `${params.x}` 참조를 쓰면 finalize에서 `bad_ref`로만 실패하고 복구 수단이 없음(세션 A 폐기 사유 중 하나). params 선언 도구 또는 finalize 시 추론 필요.
- **M6-5. 채팅 백엔드의 evaluator가 `defaultEvaluate`(제약 있으면 전부 fail).** 제약을 단 노드는 `pf_report`가 무조건 fail → "빈 제약으로 보고→확정→제약 부착" 편법이 강제됨. 실제 checker 주입 또는 "미판정" 구분 필요.
- **M6-6. `run procedures/<name>`이 프로젝트 루트 `procedures/` 배치에서 EISDIR(exit 2).** `resolveProcedureRef`가 디렉터리를 파일로 읽음. 문서 명령 패턴과 불일치. 본 테스트는 `.procforge/procedures/<name>` + 이름 참조로 우회.
- **M6-7. 증거 없는 external leaf의 golden이 dry-run 질문 텍스트로 기록됨.** replay/drift 기준을 오염시킴(관찰용 기록).
- **M6-8. `approve <이름> --node` 형태는 usage(exit 2)로 거부됨.** 절차서 모드는 `procedures/` prefix나 `.json` 접미사만 허용. 문서에 명시 필요.
- 기타 마찰: `--out .` 거부(`path escapes project root`, 하위 디렉터리+수동 복사로 우회), python 소켓 간헐 차단(WinError 10013, 재시도 통과 — runner 재시도·DNS 고정 검토), cp949 콘솔에서 비ASCII print 파손(스크립트는 UTF-8·ASCII 요약으로 회피, runner는 PYTHONUTF8 강제済).

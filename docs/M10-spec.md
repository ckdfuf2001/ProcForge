# M10-spec — OpenCode 클라이언트 실행 (유사 분석→자동 실행)

> 구현 착수 조건: M10-0 실측 완료 + 판정자 승인.
> M10-0 문서(`docs/M10-0-opencode-api.md`)의 실측 필요 항목과 1:1로 연결된다
> (§5 각 항목에 [실측 의존] 표시).

## §0 제품 방향
1. Proof는 단계를 직접 고치는 도구가 아니라, 단계의 왜(`why`)를 보고 고치는 도구다.
2. 사용자는 두 가지로 개입한다: 노드 수정 의견(M8-1 경로)과 "왜" 수정.
   둘 다 해당 노드와 하위 노드만 다시 확인 대상이 되고, 나머지는 보존된다.
3. 모든 변경에는 이유가 붙는다. 처음 분해할 때는 `why`, 재분석할 때는
   op별 `reason`이다.
4. 화면은 에이전트 구조(분석, 재분석, 실행, 검증), 진행률, 남은 작업,
   불러온 메모리, "왜"를 한 화면에 보여준다 (OmO 화면 구성 참고).
   처음부터 완성형으로 만든다.
5. 확정된 절차서는 자동 실행하되, 단계 확인은 사람이 한다.

## §1 목표 (1차 범위)
- 유사 분석: 기존 절차서 중 이번 요청과 비슷한 것을 찾아낸다.
- 재분석: 찾은 절차서를 이번 요청에 맞게 고쳐 쓴다 (새 분해가 아님).
- 단계별 가이드 UI: 고친 절차서를 사람이 단계마다 확인·진행한다.
- 순차 자동 실행: 확정된 절차서를 그대로 끝까지 실행한다.
- 2차 (범위 밖, 이번에 만들지 않음 — 요구 목록 유지):
  병렬 실행 (M11-2), To-Do 운영 (M11-1),
  교훈 집계 (M9-3, M9-2 §5 판정 4와 동일).

## §2 구조
- Proof는 OpenCode 서버의 클라이언트다. 모델 공급자는 OpenCode이며,
  Proof가 직접 LLM을 호출하지 않는다.
- 기존 MCP 표면(`pf_*` 21종)은 불변. M10 기능은 App층 신규 메서드 +
  UI 화면 추가로만 들어간다 (새 MCP 도구 추가 없음).
- OpenCode 연결은 `PROOF_OPENCODE_URL`·`PROOF_OPENCODE_MODE`·
  `PROOF_OPENCODE_TOOL_PREFIX` + `OPENCODE_SERVER_PASSWORD` (Basic auth).
  (M8-1-dogfood §1, UI 터미널 설정. M10-0 §8: 무인증 401은 1.18.32에서 확인,
  1.18.18은 미확인 — 보류 ④와 연결).
- 불변 규칙 (실측 기반):
  ① Proof는 권한에 `always`로 응답하지 않는다 (자동 승인이 계속 남음).
  ② 설정은 `PATCH /config`에 의존하지 않는다 (200이어도 GET 미반영).
  ③ `session.error`(429 포함)를 받으면 즉시 실패로 처리하고
  자동 재시도하지 않는다 (판정 4=A와 같은 방향).
- 재분석(M10-2)의 diff 초안은 OpenCode 세션에 `prompt_async`로 요청한다
  (도구 비활성 — M10-0 §3 실측 방식). 결과는 diff 초안으로만 받고
  절차서에 직접 쓰지 않는다. 요청·응답 형식은 [실측 의존] (M10-0 §2 바디 기준).

## §3 흐름별 데이터
- 유사 분석 입력: `procedures/<name>/procedure.json` (목표·노드),
  `runs/<runId>/report.json` (성공 이력), `metrics.json` (규모),
  `by-procedure/<name>/latest.json` (최근 상태). — 판정 1 [실측 의존 없음]
  (metrics는 요약 필드로만 싣고 순위에는 쓰지 않는다:
  규모가 크다고 비슷한 게 아니고, 성공 이력은 status로 이미 반영되기 때문).
- 가이드 단계 상태: `guides/<guideId>.json` (초안 경로 + runId 목록 참조).
  판정 2 = C 확정.
- 자동 실행 시 승인·취소·실패 처리: 기존 `uiRun`·`uiRunApprove`·
  `uiRunCancel` 경로를 그대로 쓴다 (재사용, 신규 실행기 없음).
  OpenCode는 실행 단계에 관여하지 않으므로 1차에 2중 승인은 없다 (판정 3).
- OpenCode 역할 표 (실측 기반):

  | 단계 | OpenCode 필요 | 이유 |
  |---|---|---|
  | 재분석 (M10-2) | 필요 | diff 초안 생성 (LLM). `prompt_async` 도구 비활성 |
  | 가이드 진행 (M10-3) | 불필요 | 상태 기록·조회만 |
  | 순차 자동 실행 (M10-4) | 불필요 | `uiRun` 경로 재사용, OpenCode 호출 없음 |

## §4 구현 커밋 분할안
- M10-1 유사 분석 조회 (읽기 전용): 절차서 목록+최근 실행 요약 API 1개.
  테스트: ① 빈 저장소 빈 목록 ② 2회 실행 절차서가 latest 기준 정렬
  ③ 텍스트 후보 필터 ④ 펼침형 요청 매칭 ⑤ done 우선 정렬 ⑥ swap 잔재 제외.
- M10-2 재분석 초안 생성: 기존 절차서 복사+요청 반영 diff 미리보기.
  테스트: ① 원본 무손상 ② diff 항목 수 일치.
- M10-3 단계별 가이드 UI: 단계 상태 저장·조회. 테스트: ① 중단 후 재개 시
  같은 단계 ② 완료 단계 건너뛰기.
- M10-4 순차 자동 실행 연결: 기존 uiRun 경로 호출 (OpenCode 호출 없음 —
  위 역할 표). 테스트: ① 끝까지 실행 ② 취소 시 run 정리 ③ 실패 시 fail 기록.
- M10-5 문서: DEV-GUIDE §8 M10 [x] + 본 사양 판정 반영.

## §5 판정 기록 (판정자 확정 + 실측 반영)
1. 유사도 기준 — **A+B 혼합 확정**: 어휘(1차, LLM 없이)로 후보를 거르고,
   metrics·성공 이력으로 순위를 매긴다 (요청 텍스트를 안 보면 "비슷한"을
   찾을 수 없음). [실측 의존 없음]
2. 가이드 단계 상태 형식 — **C 확정**: `guides/<guideId>.json`을 두고
   그 안에 초안 경로 + runId 목록을 참조로 기록한다 (가이드는 run 생전부터
   존재하므로 run 종속 불가). [실측 의존 없음]
3. 2중 승인 흐름 — **1차 범위 밖**: 실행 단계에 OpenCode가 없으므로
   2중 승인이 성립하지 않는다 (위 역할 표). [실측 반영]
4. 재분석(M10-2) 중 OpenCode 세션 끊김·오류 처리 — **A 확정**
   (즉시 실패. 실행 단계에는 OpenCode가 없으므로 판정 범위는 재분석으로 한정).
   [실측 반영: `session.error` 즉시 실패 확인]
5. M10-1 조회 범위 — **A 확정** (로컬 저장소만). [실측 의존 없음]
6. 재분석 모델 선택 — A안: `PROOF_OPENCODE_MODEL` env 추가.
   B안: 서버 기본값(GET /config/providers default 첫 항목).
   확정: **B** (env 16종 계약을 깨지 않기 위해. A 기각 이유 1줄).
   [실측 의존 없음]
